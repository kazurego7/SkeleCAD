# 工程の先行処理と表示キャッシュ

分割の更新が完了し、有効な関節候補があるモデルは、入力が3秒間変わらなければ
ジョイント加工、Bambu用の配置・サポート付きスライスを順に先行処理する。
作業中の工程は切り替えず、ジョイントの準備ができた時点で工程から利用できる。
途中で加工・プリント準備を要求した場合は、同じ入力の先行処理を引き継ぐ。

## 連続編集と公開条件

- 元のSTL、分割マニフェスト、選択マーカー・関節、設定、ツール構成、実装の
  SHA-256から入力を識別する。工程状態だけの変更では形状の識別を変えない。
- 計算はジョブ内の専用スナップショットで行う。完成した結果はリクエスト処理と
  同じロック内でもう一度入力を照合し、最新である場合だけ公開する。
- 古い入力になった加工は、処理の区切りで協調的に終了する。CAD・形状処理の
  実行中の1操作を強制停止する方式ではない。
- 先行処理は同時に1件。前面のキューがある間は別の先行処理を開始しない。
  Windowsでは優先度を下げ、数値演算ライブラリのスレッド数を1に抑える。
- プロセスIDと作成時刻を保存し、サーバーの再起動で同じ作業を二重起動しない。
  終了済みの専用スナップショットは削除し、リクエスト・結果・ログを残す。

先行スライスは `verification_run=true`、`ready_to_print=false` のまま保存する。
「プリント準備」を押した際には、現在確認している姿勢をサーバーでも検証する。
元部品、設定、ツール本体、監査実装、3MFのすべてが検証時と同じであれば、
検証済みのスライスを利用して現在の確認に結び付ける。欠落や変更があれば通常の
準備と監査を実行する。この処理でプリンターへの送信は行わない。

## 表示と操作

- STLの取得・ハッシュ照合・読み取りは専用Workerで行う。表示要求を先読みより
  優先し、操作直後は次の先読みの開始を遅らせる。
- 読み取った形状は内容のハッシュで識別し、128 MiBまで保持する。
- 描画用の配列とGPUバッファには256 MiBの上限を設け、古いものから破棄する。
  この上限はアプリ全体のメモリ上限ではない。表示中の形状やブラウザー、衝突判定の
  データなどは別に必要となる。
- 衝突判定のWorkerは最新の1組を保持し、同じ形状・関節・接触条件で戻った場合に
  再利用する。別の形状や条件では作り直し、古い姿勢の応答は表示に採用しない。
- 前の工程へ戻る際も、入力や加工結果の識別が同じなら再取得・再描画準備を省く。
  キャッシュに収まらない大きなモデルや、更新直後の初回表示には読み込みが必要。
- 工程の処理が終わっても、ユーザーが見ている別の工程を勝手に切り替えない。

## 確認結果（2026-09-05）

入力はユーザー提供のプテラノドン。7部品・6関節のモデルで確認した。

| 操作 | 実測 |
| --- | ---: |
| 先読み済みの外観を表示 | 7.4 ms |
| 分割工程へ戻る（描画キャッシュ使用） | 3.4 ms |
| 先行加工済みのジョイントを初めて表示 | 17.2 ms |
| 外観・分割を経由してジョイントへ戻る（描画・衝突判定を再利用） | 1.1 ms |
| 先行スライスを現在の確認に結び付ける処理 | 3.14秒 |

表示時間はビュワー内部の描画準備時間で、クリックからの通信時間や初回の
衝突判定準備を含まない。最初の実装では印刷準備の再検証に24.09秒かかっていたが、
検証済みバイト列の照合による再利用後は3.14秒となった。再利用前後の3MFハッシュは
完全一致し、現在の確認姿勢の検証は実行される。

256 MiBの描画キャッシュで3工程を往復し、保持量185,399,712バイト、
描画キャッシュと衝突判定Workerの両方の再利用、読み込み表示なしを確認した。

別の通し検証では、加工開始後に分割を2回更新し、古い結果が破棄されること、
最新の加工途中から要求してもCADを二重起動しないこと、印刷準備まで先行結果を
引き継ぐことを確認した。記録は `.runtime/background-live-*/qa.json` に保存する。
合成モデルのみでの合格判定にはしていない。

自動検証は `test_workflow_background.py`、`test_workflow_print_release.py`、
`test_workflow.py`、`test_viewer_server.py` とビュワーのソーステストで行う。
起動済みサーバーには新しいPython実装と配信対象を読み込ませるための再起動が必要。


## ジョイントの逐次検査（2026-09-05）

加工時は直前の分割と比較し、位置・範囲・左右ペア・配置方法が変わったマーカーを
優先する。左右対称ペアは分離せず、各関節に必要な親・子パーツの仕上げが終わった
時点で同じ軸探索と接続位置検査を行う。失敗したら残りのパーツ仕上げを待たず終了する。
仕上げは各パーツ1回だけ行い、成功時の出力・ブーリアン演算・体積保存検査は元の
パーツ順序を維持する。工程を表示し直すだけでは優先対象や形状を変更しない。

軸探索内では、同じ関節・同一の方向ベクトルに対する光線検査の結果を一時保持する。
粗い探索、詳細探索、反対向きの探索、採用時の再取得で同じ計算を繰り返さない。
探索範囲、角度刻み、埋め込み量、点の内外判定、最終形状検査は変更していない。
このキャッシュは1回の軸探索内だけ有効で、別形状へ持ち越さない。

比較記録は `.runtime/axis-speed-qa/comparison.json`、工程別時間は同ディレクトリの
`results.json` に保存する。元のユーザーモデルは変更せず、コピーした入力から
変更前と変更後を同条件で加工し、STL全バイト・関節情報・衝突検査・体積保存を照合する。


同じ入力・設定、既存キャッシュなしで変更前後を各1回比較した結果：

| プテラノドンの配置 | 変更前 | 変更後 | 検証 |
| --- | ---: | ---: | --- |
| 軸探索が失敗する配置 | 33.85秒 | 20.01秒 | 同じマーカー・同じエラー |
| 成功する4パーツ・3関節 | 34.59秒 | 34.01秒 | 全STLバイト・関節・衝突・体積保存が一致 |
| 成功する7パーツ・6関節 | 58.98秒 | 53.87秒 | 全STLバイト・関節・衝突・体積保存が一致 |

いずれもジョイント加工のみで、印刷準備を含まない。単回計測のため実行負荷による
変動はあり、すべての配置で同じ短縮率を保証するものではない。加工の成功・失敗条件、
寸法、角度刻み、仕上げ精度は維持している。

## 加工中の可動域表示（2026-09-05）

分割の保存・加工中も可動域へ移動できる。前回の検査済みモデルがあれば表示を維持し、
変更したマーカーの関節だけを固定する。近傍の未変更関節は前回形状で操作できる。これは前回形状の確認用であり、新しい入力での
全体検査完了を意味しない。連続したマーカー編集は既存の保存待ち処理で最新状態へまとめる。

新しい加工は各パーツの最終メッシュ検査を終えるたび、不変の部分プレビューを公開する。
親子両方のメッシュが完成した関節から操作を許可する。軸探索・CAD演算の途中では
新しい最終メッシュはまだないため、前回モデルを保持する。初回生成ではこの間の可動域は
確認できない。部分結果は印刷不可で、最終の衝突・体積保存検査を省略しない。
最終検査失敗後は未認証の部分結果を操作不可にし、前回の検査済みモデルがあればそちらを使う。

読み込み完了まで旧メッシュを残し、切替時にカメラ・選択・関節姿勢を引き継ぐ。
関節の中心・軸・祖先の構成が変わった枝は姿勢をリセットし、他の枝は維持する。
新しい形状では衝突確認を再実行する。古い入力の部分結果は公開・取得を拒否する。

実モデル検証ではプテラノドンを4パーツ・3関節から7パーツ・6関節へ変更し、
加工中の旧モデル操作、段階公開、最終モデルへの切替を確認した。
最終の7個のSTL全バイト・関節情報・衝突検査・体積保存量は変更前と一致した。
記録は `.runtime/seamless-live-20260905-135753/` の `events.json` と `comparison.json`。
この計測では分割要求から機械加工完了まで約64秒、印刷準備完了まで約98秒だった。
以前の加工単独の計測とは測定範囲が違うため、総処理速度の改善を示す数値ではない。
姿勢の非ゼロ値の引継ぎ、変更した枝だけのリセット、部分結果の操作・印刷制限も自動検証する。

## Windowsの結果保存競合（2026-09-05）

途中結果の `result.json` を原子的に置き換える際、Windowsの読み取りハンドルが
削除共有を許可していないと WinError 5 / 32 / 33 が起こり得る。
共通の `write_json` はこの3種類に限って置き換えを最大20回再試行する
（待機合計約1.75秒）。待機中は従来の完全なJSONを維持し、直接上書きはしない。
恒久的な拒否や他のI/Oエラーは隠さず通知し、作業用ファイルは可能な限り除去する。
`test_workflow_json.py` では実際のWindowsハンドルによる競合、恒久拒否、
無関係なI/O障害、更新前後の内容と作業用ファイル除去を検証する。

## CAD失敗の診断記録

CADの子プロセスが異常終了した場合、出力全文を `worker.log` にも記録し、
最後のエラー行（最大300文字。出力がなければ終了コード）を公開エラーへ含める。
失敗した先行処理を片付ける前に `.background/<attempt>/diagnostics/` へ
各工程のログ・request.json・status.json・source_manifest.jsonを保存する。
大きな作業用形状は従来どおり除去する。診断記録はローカルだけに保持する。
ログ保持・片付けとCAD異常終了の詳細伝達を自動テストで確認する。

## スライスをBambu Studioへ移す（2026-09-05）

現在の通常ワークフローでは先行処理・プリント準備のどちらも
`prepare_workflow_project.run` を使い、スライサーを起動しない。
配置・サポート設定を入れた編集可能な3MFを開き、利用者がBambu Studioでスライスする。
事前スライス用の旧処理は削除。スライスは Bambu Studio で行う。
新しいリリースは `artifact_kind=bambu_project`、`ready_to_open=true` を使い、
`ready_to_print=false`、`slicing_verified=false` を維持する。前の工程の形状・姿勢確認、
3MFと元形状の一致検査、ハッシュによる更新検知は省略しない。

メッシュのXMLは同じ12桁の有効数字と三角形順を保ち、文字列をまとめて生成する。
変更がない検査済みプロジェクトは、形状・設定・実装・テンプレート・出力ハッシュを
照合して再利用し、承認のハッシュだけを現在の確認内容へ結び直す。

9パーツ・1プレートで、スライスなしの旧書き出し13.61秒、新書き出し10.43秒、
検査済み結果の再利用0.12秒（単回計測）。頂点・面・配置・設定の一致とG-codeなしを確認。
試験スクリプトと結果は `.runtime/unsliced-bench/` にある。通常処理の
サポート形状や印刷時間見積もりは、Bambu Studioでスライスした後に確認する。
