# Hunyuan形状生成の最適化（2026-09-05）

現在は追加の7方式比較を経て、情報を省略しない`hierarchical_full`を採用しています。
設定・検証結果は[階層方式の検証記録](HUNYUAN_HIERARCHICAL.md)を参照してください。
以下はFlashVDMの初回採用と、その後の撤回の履歴です。

## 追加検証による採用撤回

ユーザーの翼付き骨格モデルで、FlashVDMが腕の穴と足首のバリを発生させることを確認しました。
同じ処理済み入力・Seed 3407・50ステップ・guidance 5.0・解像度384を通常方式で再生成し、
同じ後処理を通すと、穴のない1成分のメッシュとなり、拡大画像でも両方の不具合が消失しました。
FlashVDM側には後処理後も142本の境界辺・3つの開いた境界が残っていました。
初回の1画像・2 Seedによる検証では、この細い骨格形状の劣化を検出できませんでした。

そのため**既定は`inference_decoder: vanilla`、`num_chunks: 8000`に戻しました**。
FlashVDMは実験用の明示指定のみとし、一般的な品質維持や高速化を保証しません。
新しいPython・ライブラリ環境はそのまま使用しています。既存のユーザーモデルは上書きしていません。
比較用生成物と拡大画像は`.runtime/hunyuan-hole-check/`に保存しています（Git対象外）。

以下は採用撤回前のロボット画像による測定記録です。現在の既定設定ではありません。

## 初回の測定記録

画像ワークフローにFlashVDMの表面計算を採用しました。Hunyuan3D 2.1の重み、
FP16、50ステップ、guidance 5.0、要求解像度384は維持します。
`enable_flashvdm(replace_vae=False)`でVAE重みの交換を避けています。

## RTX 3060 12 GBでの測定

自作の`assets/workflow_tests/blue_robot.png`を通常の背景処理に通し、Seed 3407と3408で比較しました。
測定中は他の生成や描画を並行実行していません。

| 条件 | 通常方式 | 採用したFlashVDM |
| --- | ---: | ---: |
| Seed 3407・推論 | 220.47秒 | 100.33秒 |
| 同・読み込みと書き出しを含むスクリプト全体 | 262.12秒 | 150.06秒 |
| 同・PyTorch最大割当メモリ | 7814 MiB | 7948 MiB |
| 同・PyTorch最大予約メモリ | 8736 MiB | 9552 MiB |
| Seed 3408・表面計算 | 125.70秒 | 5.92秒 |
| 同・拡散94.47秒＋表面計算 | 220.17秒 | 100.39秒 |

Seed 3407は別プロセスによる実生成、3408は同じlatentを各方式で展開した比較です。
後者の合計には共通の拡散時間を加算しています。ロード時間はキャッシュ状態にも左右されます。
メモリ値はPyTorchの測定であり、画面表示などを含むGPU全体の使用量ではありません。
スクリプト全体で約43%、推論部分で約54%短縮しました。アプリの後処理やCAD加工は別です。

## 形状検証

FlashVDMは要求384に対して内部グリッドを380へ調整します。上流の表面座標換算と組み合わさり、
未調整のGLBでは体積が約3%小さくなりました。アプリ既存の`normalize_mesh`で
各形状を中央配置・全長120 mmに揃えた後に、製作で使う形状を比較しています。
生のGLBをそのまま寸法付きの製作用データとして扱わないでください。

| 通常の後処理後 | Seed 3407 | Seed 3408 |
| --- | ---: | ---: |
| 体積差 | +0.02470% | +0.00755% |
| 表面距離の平均 | 0.00343 mm | 0.00349 mm |
| 表面距離の95%点 | 0.01026 mm | 0.00978 mm |
| サンプル内の最大表面距離 | 0.05221 mm | 0.06747 mm |
| 閉じたメッシュ・面の向き | 正常 | 正常 |
| 連結成分 | 各1 | 各1 |

距離は双方向に各5000点を面積に応じて抽出し、相手の三角形表面まで測定しました。
全表面の誤差上限を証明するものではありません。各方式で頂点配置が異なるため、
最近傍「頂点」距離（平均約0.114 mm）とは区別しています。
Seed 3407のFlashVDM生出力には退化面が2枚あり、既存の後処理で除去すると閉じたメッシュになりました。
4枚の同一視点プレビューを確認し、頭・腕・脚・足の欠落や目立つ変形はありませんでした。
検証は1画像・2 Seedの形状生成のみです。別の画像やテクスチャ生成での性能・品質は未検証です。

## 比較した他の方式

- 通常方式の`num_chunks`を8000から32000へ増加：2 Seedとも約212秒、約4%の推論短縮。
  形状差は最大0.00011 mm以下（最近傍頂点）でしたが、FlashVDMの効果が大きいため既定にはしません。
- 階層方式（`adaptive_kv_selection=False`）：最終グリッドで空のTensorリストとなり失敗。
  本番の選択肢には含めません。上流ソースは改変していません。

## 設定と再検証

`config/parameters.json`の`image_workflow`:

```json
{
  "inference_decoder": "flashvdm",
  "num_chunks": 8000,
  "steps": 50,
  "octree_resolution": 384
}
```

新規ジョブはこの設定を保存して実行します。過去の設定に方式指定がない場合は通常方式を使います。
通常方式へ戻す場合は`inference_decoder`を`vanilla`にし、時間目安も従来の値に戻します。
単独の`src/generate_hunyuan_shape.py`は互換性のため既定が`vanilla`です。
FlashVDMは`--decoder flashvdm --num-chunks 8000`で指定できます。
各生成のJSONに方式、時間、GPUメモリを記録します。

比較ツールは`tools/compare_hunyuan_meshes.py REFERENCE CANDIDATE --output REPORT.json`です。
両入力を先に通常の後処理に通してください。比較ツール自身は位置合わせしません。
実行ログ・GLB・STL・比較画像・測定JSONは`.runtime/hunyuan-optimization/`にあり、Git対象外です。

画像ワークフロー28テストが合格しました。既存の組立形状・関節寸法・材料・生成物は変更していないため、
本最適化で既存CAD/STL・衝突・CalculiXの再生成は行っていません。
